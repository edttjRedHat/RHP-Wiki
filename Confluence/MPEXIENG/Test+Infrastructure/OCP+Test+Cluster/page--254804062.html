Test Platform Integration

CI Operator

Worklow

A Job in CI Operator, normally involve the workflow that deploy the CUT, which this procedure alone can take 40-50 minutes, and a long must-gather process during post test, adding another 20-30 minutes. A special workflow, named external-cluster, exists allowing directly connect to an existing OCP Cluster (that may be deployed outside the CI Operator itself). Using this workflow will significantly shorten the Job Rehearsal time in a Pull Request (PR).

This ONLY make sense if a Cloud-based Cluster is used for CUT. For Bare Metal Cluster, since each Cluster Profile represent exactly one single instance, while this workflow can still be used, but it simply does not make sense to do so.

Please follow these instructions.

  1. Create personal Secret Path in CI Operator Secret Vault. Please follow the instructions in CI Operator Guide. The Providing Credential procedure MUST be followed to connect it to the used Cluster Profile.

  2. Store the corresponding KUBECONFIG and optionally the KUBEADMIN_PASSWORD_FILE, those are associated with the "external" OCP Cluster in this personal Secret Path.

    Since we can only use one K8s Secret for each Cluster Profile and the current implementation in CI Operator it to merge the content of multiple Vault Secrets if those are configured to be synchronized to the same Secret Name, a special care is needed to avoid any Secret Key Collision (as there is no way to predict which Secret is overriding as the final content). Please use a unique Secret Key Name inside the Vault Secret to add user specific kubeconfig and kubeadmin-password file (make SURE those 2 files use the SAME suffix and the the file name and suffix connector, i.e. --, IS important):

    yamlPersonal CI Operator HashiCorp Vault Secret item.--: "" kubeconfig----: "" secretsync/target-name: "" secretsync/target-namespace: "ci"]]>BEWARE that the Keys from the personal CI Operator HashiCorp Vault Secret item may potentially clutter ALL Jobs that uses the Cluster Profile it synchronizes to. So please be a good citizen by NOT forgetting to remove the synchronizer Keys (at least the secretsync/target-name Key) or rename them by removing the secretync/ after you are finished with the PR.

  3. In the PR's Head Commit, update the corresponding Job Configuration file.

    ci-operator/config/<GitHubOrg>/<GitHubRepo>/<GitHubOrg><GitHubRepo><GitHubBranch>__<JobVariantDescription>.yaml

    yaml-- ... ... workflow: external-cluster ... ... - ... ...]]>

  4. After all the Job Rehearsals in the PR yield the expected results, the changes from the above Step 3 can be reverted back. A final Job Rehearsal using the final intended Job Configuration then may be carried out as final PR test.
